# Правила для кодингового агента

Проект ведётся по Spec-Driven Development: спецификация первична, код ей соответствует.

## Порядок работы

1. Перед изменением кода прочитай `spec/product/` и `spec/tech/`.
2. Если задача меняет поведение, сначала обнови нужную спецификацию, потом код.
3. Запусти проверки:
   - фронтенд: `cd app/frontend && npm run build` (проверка типов и сборка);
   - `tests/` и `benchmark/` — когда появятся; команды запуска будут описаны в их README.
4. Добавь запись в `CHANGE_HISTORY.md`: дата, что сделано, кто.
5. Не используй готовые поисковые индексы (см. ниже).

## Жёсткие ограничения

- **BM25 реализуется самостоятельно.** Запрещены `rank_bm25`, Elasticsearch, Whoosh, Lucene, `BM25Retriever` из LangChain и LlamaIndex и любые аналоги. Библиотеки для лемматизации (например, `pymorphy3`) разрешены.
- **Запрос проходит ту же предобработку, что и документы.**
- **Не выдумывай.** Если чего-то нет в спецификации или коде — ставь `TODO:` и задай вопрос, а не подставляй правдоподобное значение. Это касается корпуса, списка городов, модели LLM, метрик.
- **Секреты не коммитим.** Ключи LLM и прочее — только в `.env`, он в `.gitignore`.
- **Дизайн не меняется без явной просьбы.** Цвета, формы и тексты интерфейса утверждены; значения лежат переменными в начале `app/frontend/src/styles.css`.

## Git

- Небольшие осмысленные коммиты, сообщения на русском.
- `git push` — только после подтверждения человеком.

## Соглашения

- Документация и тексты интерфейса — на русском.
- Код, документация и результаты benchmark должны соответствовать друг другу: изменил формулу, параметр или формат API — обнови `spec/tech/` и перезапусти benchmark.
- Фронтенд получает маршрут через одну функцию `buildRoute` в `app/frontend/src/state.ts`. Подключение бэкенда — замена этой функции на запрос к API; типы `Plan`, `RouteDay`, `Stop` должны совпадать с форматом из `spec/tech/architecture.md`.
