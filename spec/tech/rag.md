# RAG и BM25

Автоматический benchmark проверяет только собственный BM25: один полный вопрос →
одна ранжированная выдача документов. LLM, JEV, планировщик, API и OSRM не вызываются.
По умолчанию отсечения нет: k равно числу документов корпуса (сейчас 30).
`--k 3` явно ограничивает оценку первой тройкой. Результаты — `results/bm25.json` и `bm25.md`.

## Корпус

Источник — `Иваново.json` в корне проекта. Рабочий корпус — 30 фиксированных
JSON-документов в `app/backend/data/ivanovo/`. Каждый файл имеет собственную
категорию: одна исходная рубрика — один файл, без разделения рубрики на части.
Все места выбранной рубрики собраны в её единственном документе.
Список 30 категорий и количество мест — в `app/backend/data/README.md`.
Если в исходнике только одно подходящее место рубрики, документ содержит одно место.

Все 30 документов содержат `id`, `name`, `city`, `category` и `places`.
Общего `text` в JSON нет. У каждого места — индивидуальный `text` одним абзацем,
координаты и ссылка на источник. В описания входят название, исходная рубрика,
адрес и доступные сведения из `Иваново.json`. Искусственных ключевых слов нет.
Данные не дополняются выдуманными услугами, расписаниями и ценами.

Добавляется один короткий фрагмент реального отзыва с автором и датой:
сначала из исходного JSON, при его отсутствии — с Яндекс Карт по тому же ID.
Длина фрагмента — до 240 символов; сокращение отмечено многоточием.
Если отзыв не найден, текст остаётся без цитаты. URL отзыва не индексируется;
ссылка на организацию остаётся в `source`, отзывы — по адресу с `reviews/`.
Отзывы являются мнениями посетителей. Рейтинг записывается кратко, без «из 5».
D01 сохраняется в уже просмотренном виде.

Загрузчик соединяет индивидуальные тексты в памяти для индекса.
Единица BM25 в benchmark — файл с ID D01–D30, не отдельное место.
В маршрутном графе дополнительно ранжируются места, входящие в найденные
документы; координаты берутся из записей мест.
Происхождение — в `app/backend/data/README.md`. Генерация при запуске не выполняется.

## Поиск

Собственный BM25, k₁ = 1,2, b = 0,75. Готовые поисковые индексы запрещены.
Индекс строится при запуске. Одинаковая предобработка текста и запроса:
NFKC → casefold → слова и числа → pymorphy3, первая нормальная форма
→ удаление фиксированного списка служебных слов из `preprocessing.py`.
Одна функция применяется к документам и запросам; отрицания «не», «нет», «ни»
и слово «без» сохраняются. Числа, тематические слова и повторения сохраняются.
Корпус, вопросы, эталоны и параметры BM25 при этом не меняются. Лемматизация может ошибаться на неоднозначных словах;
синонимы автоматически не распознаются. Эталоны не подставляются в тексты
и не используются при поиске.

k = 3 означает три документа-подборки, а не три места.
Число мест в контексте зависит от размера найденных подборок.
Поиск не гарантирует покрытие всех частей составного запроса.

## Benchmark

`python -m benchmark.run` загружает корпус и `benchmark/questions.json`.
Поиск получает только полный текст `question`, город и лимит. Интересы,
эталонные категории и relevant_ids не передаются поиску. Нет фильтрации по целям.
Индекс и предобработка те же, что в приложении.

Для каждого обычного вопроса: Recall@k — доля relevant_ids, найденных в выдаче;
RR@k — обратная позиция первого релевантного документа или 0. Recall@k и MRR@k
усредняются по обычным вопросам с одинаковым весом. Метрики вопросов с пустым
эталоном не считаются; выдача пяти вопросов без ответа сохраняется отдельно.
Правильность ответов и корректность отказов этот прогон не оценивает.

По умолчанию k = числу документов корпуса; возвращаются только документы
с положительным баллом. Можно явно задать `--k 3` или другой положительный лимит.
В отчёте указывается фактический k; полная выдача не подписывается Recall@3.

## Поэтапный маршрут с BM25

Для однодневного маршрута планировщик определяет типы остановок и ограничения
порядка из настроек и пожеланий. Для каждого типа независимо ищутся все
документы с положительным баллом BM25 в подходящих рубриках корпуса; затем тем же BM25 ранжируются
отдельные места внутри найденных документов. На вход JEV поступают до пяти
мест с координатами, не использованных ранее. Основное и запасное место должны
происходить из этих кандидатов. После выбора OSRM оптимизирует порядок с учётом
ограничений планировщика. Если нужная остановка не найдена, её не заменяют
выдуманной или несвязанной категорией; в ответе отмечается нехватка мест.

Benchmark выполняет один поиск по полному вопросу и 30 документам, без фильтра
категорий. Поиск по целям относится только к приложению. В диагностических
логах приложения доступны категория, ID найденных документов и баллы.
LLM и сетевые сервисы поисковым benchmark не вызываются.

## Сохранённые проверки пайплайна

Прежние прогоны маршрута остаются в `benchmark/results/pipeline.json` и `pipeline.md`.
Нынешний benchmark их не перезаписывает. Контекст `capture_retrievals` в маршрутном
retriever сохранён для отдельной диагностики приложения.

## Поиск без отсечения документов

Маршрутный retriever больше не обрезает выдачу документов до трёх: запрашивается
весь индекс с сохранением фильтров города и категории. Возвращаются только
документы с положительным баллом BM25, в прежнем порядке ранжирования.
До пяти отдельных мест передаются JEV, как прежде. Старые метрики Recall@3
относятся к прежнему прогону; полную выдачу нельзя подписывать Recall@3.
