# Архитектура

Однодневное приложение: React + TypeScript → FastAPI → собственный BM25 → LLM → OSRM.
Один файл корпуса — один поисковый документ, содержащий несколько мест.

## Папки

| Путь | Назначение |
|---|---|
| `app/frontend/src/` | Интерфейс, HTTP-клиент, карта Leaflet |
| `app/backend/main.py` | FastAPI, endpoint, подключение генератора, обработка ошибок |
| `app/backend/api/schemas.py` | Формат запроса и ответа, только days=1 |
| `app/backend/pipeline_adapter.py` | Соединение BM25, выбора мест и OSRM с API |
| `app/backend/domain/models.py` | Place, SearchDocument, SearchHit без HTTP-зависимостей |
| `app/backend/infrastructure/search/` | Собственный BM25 и общая предобработка |
| `app/backend/infrastructure/corpus/loader.py` | Загрузка 30 документов |
| `app/pipeline/rag/routing.py` | Используемый клиент OSRM и обработка его ответа |
| `app/backend/data/ivanovo/` | 30 категорий, 336 мест, индивидуальные тексты |
| `benchmark/` | 15 вопросов, поисковые метрики и сохранённая выдача |
| `tests/` | Проверки BM25, API и соединения компонентов |

## Путь запроса

1. `buildRoute` передаёт город, интересы, дату и пожелания в FastAPI.
2. Планировщик выбирает категории остановок и ограничения порядка.
3. Для каждой категории BM25 ранжирует все документы с положительным баллом, прошедшие фильтры; отдельный BM25 по
   местам ранжирует вложенные места этих документов. Поиск benchmark остаётся
   одним поиском по 30 документам и полному вопросу, без фильтра по категориям; по умолчанию выдача не обрезается.
4. JEV выбирает основную и запасную точки из полученных кандидатов; по умолчанию
   при сбое JEV используется порядок BM25. Результат сверяется с кандидатами.
5. OSRM оптимизирует путь с учётом ограничений и строит пешую геометрию.
   API возвращает один день и помечает недостающие остановки.

Названия, рубрики, адреса и координаты берутся из корпуса. Поиск не использует
pgvector и эмбеддинги. Зависимости langgraph и langchain-openai нужны для
существующего графа и планировщика.

## Корпус и поиск

Файл имеет id D01–D30, name, city, category и places. У каждого места свой text,
исходный ID, адрес, координаты и source. Общего text в JSON нет:
загрузчик соединяет описания в памяти для индекса benchmark. В нём вложенное
место не является отдельным документом. Для маршрутного графа создаётся
дополнительный индекс отдельных мест с тем же BM25; исключения мест
применяются к этому индексу.

Индексы документов и мест строятся один раз при создании генератора. Для benchmark по умолчанию k равно числу документов; можно явно задать --k. k₁=1,2, b=0,75.
Предобработка документов и запросов одинакова: лемматизация и стоп-слова.
Подробности — в [rag.md](rag.md), формат HTTP — в [api-contract.md](api-contract.md).

## Настройки и зависимости

`.env`: ROUTERAI_API_KEY, ROUTERAI_BASE_URL, CHAT_MODEL, OSRM_BASE_URL,
необязательные CORPUS_PATH и JEV_MODEL. Путь корпуса по умолчанию — app/backend/data/ivanovo,
относительные пути считаются от корня проекта. Секреты в Git не добавляются.
TRIP_GENERATOR_FACTORY позволяет заменить генератор для проверок.

Корневой requirements.txt включает app/backend/requirements.txt.
PostgreSQL, pgvector и эмбеддинги не нужны для API. Маршрутный граф и JEV используются с собственным BM25.
Compose запускает OSRM. Карта фронтенда использует leaflet и @types/leaflet.

## Разделение работы

Дарья: корпус, поиск, предобработка, benchmark.
Анна: интерфейс, настройка внешних сервисов и проверка интеграции.
Общие контракты и изменения интеграции согласуются вместе.
Ветки: bm25-benchmark и integration; проверенная версия — main.

Текущая интеграция маршрута восстанавливает поэтапный граф: планировщик →
BM25 по каждой цели → выбор кандидатов → OSRM. Benchmark использует обычный
BM25 по полному вопросу; поэтапная выдача маршрута проверяется отдельно.
